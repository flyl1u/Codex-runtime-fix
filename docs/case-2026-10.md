# 案例：Primary Runtime 部署失败伴随原生闪退

记录更新：2026-10-11。时间线使用北京时间。设备和用户身份已移除。

## 环境与症状

分析时的 Codex 应用版本为 `26.1002.52244`，构建号 `13536`；Windows 应用包版本为 `26.1002.7124.0`。需要部署的运行框架为 `OpenAI.CodexPrimaryRuntime.v26-1007-641-0`，版本 `26.1007.641.0`，架构 x64。

用户报告启动不久及执行任务期间反复闪退。清理渲染缓存、禁用 GPU 后，正常 Windows 应用入口启动的实例仍然退出，因此这些操作未解决捕获到的故障。直接启动可执行文件的对照实例与正常应用入口的环境不同，其短时稳定结果没有被作为修复证据。

## 证据链

| 阶段 | 观察结果 | 能支持的结论 |
| --- | --- | --- |
| 10 月 9 日本地转储分析 | `windows-updater.node+0x1a789` 空指针读取，异常 `0xc0000005`，位于 `libuv-worker` | 此次捕获到的直接故障位置在原生部署组件 |
| PE unwind 与接口定位 | 调用链与 `IPackageManager9.AddPackageByUriAsync` 的框架部署路径对应 | 运行框架部署失败路径需要调查 |
| 标准安装对照 | 同一已验证签名的 MSIX 安装失败，`0x80073CF6` / `0x8007007E` | Windows 部署链路也存在问题 |
| DISM 完整扫描 | 组件存储可修复 | 存在可由系统工具处理的组件问题 |
| DISM RestoreHealth | 成功完成，记录为无需重启 | 本次 Windows 组件修复成功 |
| 修复后标准安装 | 同一框架成功安装，`Status=Ok`，AppX 部署成功事件 | 原先失败的框架部署已恢复 |
| 10 月 11 日回访 | 用户报告不再闪退；当前应用包版本为 `26.1007.2314.0` | 实际使用症状已改善；期间也发生了应用更新 |

同一个框架包的 SHA256 在安装前后核对一致。公开仓库仅记录版本和操作结果，不分发该安装包，也不将这一历史版本作为其他用户的安装目标。

## 一条曾被高估的线索

曾发现一条旧 WindowsAppRuntime 1.6 部署扩展登记，指向缺失的 DLL。由于它与“模块找不到”的错误吻合，最初把它视为较强候选。

但随后独立的 64 位注册表只读核对确认：**该登记在框架成功安装之后仍然存在。** 因而它不是本次安装恢复必须删除的项目，也不能认定它是唯一根因。公开操作步骤不包含删除它。

## 验证的限制

早期用于验证的监测脚本因读取正在写入的日志时使用了不合适的共享模式而中止。这是采集脚本失败，不能解释成应用再度闪退，也不能把它写成“连续 10 分钟监测全部通过”。新的公开采集器使用允许并发写入的只读文件共享方式，并对采集失败单独记录。

本案例没有取得足以确认“具体哪一个 Windows 文件导致部署错误”的证据，也没有证明 DISM 是长期稳定性改善的唯一原因。它能提供的是部署失败前后的对照结果、排查方式和用户后续反馈。
